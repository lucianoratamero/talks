What is Atomic Design?

Design system methodology by Brad Frost

Divides the design into five composable stages

Complexity as a spectrum

Granular control in one big block can be cumbersome

Exposing atoms directly is a bit much

And no control might give the editor analysis paralysis

Exposing only templates will require a lot of documentation and experience

Case study: firefox.com

We were hired to build the new design and add Wagtail as a CMS

How we built (and rebuilt) our cards

In the previous design, there was only one type of card

When implementing the new design

We went with multiple blocks

Different fields

And templates

To keep design consistency

And make the editors know exactly what to use

After a few months

We started to notice some very small antipatterns

So we merged the ones that were generally used

And kept the single use ones separate

When inheriting a system

Resist the temptation to keep the patterns that are there, but more importantly keep your editors in the loop

The Media + Content conundrum

Cut the problem into pieces

  • We kept our settings minimal
  • Used generic blocks as much as possible

Created a Media block

  • It encapsulates images, videos, animations, etc.
  • Made it the default for media everywhere

I <3 Stream Blocks

They allow us to reuse blocks,

validate the content before publishing

and remove complexity form the parent block

Lessons learned

  • Blocks within blocks give you a new dimension you can use to extract complexity
  • Atomic Design's biggest strength is composability, and Stream Blocks are great for that
  • Hiding complexity is key, or "Sometimes all you need is a bit of CSS"

LLMs are great for documentation

  • Non-technical people need something they can not only read, but play and experiment with
  • We built database fixtures that contain sample pages with self documenting blocks
